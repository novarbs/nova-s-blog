こんにちは、リラです。  
いま個人開発で「ツクシフ」というシフト自動作成ツールを作っています。完成品の紹介ではなく、開発途中の現在地をまとめる記事です。

## 解きたい課題

コンビニや飲食店の店長は、毎月クルーの希望を集めて、紙やExcelでシフトを組んでいます。希望をなるべく叶えつつ、必要な人数を埋めて、労働時間の偏りも抑える。これは人間がやるにはかなり重い作業です。

ツクシフでは、この流れを次のように置き換えます。

1. クルーがWebから出られる日時と備考を提出する
2. システムが数理最適化でシフト案を自動生成する
3. 店長が日別に手直しして確定・公開し、PDFを出力する

## 技術構成

- **フロントエンド**: React + TypeScript + Vite（クルー向けと店長向け管理画面）
- **バックエンド**: Python 3.12 + FastAPI
- **最適化エンジン**: OR-Tools（CP-SAT）
- **自然言語処理**: Claude API（備考の解析のみ）
- **DB / キュー**: PostgreSQL 16 + Alembic / Redis 7（生成はワーカーで非同期実行）
- **開発基盤**: Docker Compose、pytest

## 設計の考え方 — ソルバーとLLMの線引き

「AIでシフトを作る」と聞くとLLMに丸ごと任せる構成を想像しがちですが、ツクシフでは役割をはっきり分けています。

**シフトの割当そのものはOR-Toolsで解きます。** 必要人数の充足、1日8時間・週40時間の上限、高校生の深夜勤務禁止、夜勤明けの休息といった制約は、間違えてはいけないルールです。ここは制約充足問題として定式化し、ソルバーに厳密に守らせます。

**LLM（Claude API）に任せるのは、自由記述の備考の解釈だけです。** 「15日以降はテスト期間なので入れません」のような自然文を構造化データに変換します。ただし、解釈結果を自動でハード制約にはしません。誤読があると「入れると言った日に入れない」事故になるので、あくまで店長が確認するための材料として提示し、確度の低いものは `needs_manager_attention` フラグで明示します。カレンダーの回答と備考が食い違っている場合も、矛盾として店長に見せます。

```python
class NoteAnalysis(BaseModel):
    summary: str          # 店長向けの1文要約
    unavailable_dates: list[date]
    contradictions: list[Contradiction]
    needs_manager_attention: bool = False
```

APIキーが未設定でも、解析に失敗しても、シフト生成自体は止まらない設計にしています。

## 途中で変えたこと — 枠モデルから必要人数モデルへ

当初は「早番・遅番」のような固定枠を店長が定義し、そこに人を割り当てるモデルで実装していました。ところが、知人の店舗で実際に使われている紙のローテーション表を見せてもらったところ、**固定の枠は存在しませんでした。** 時間軸に名前の横棒を自由に引いていて、「7時から入ってもらう」といった調整が普通に行われていたのです。

そこで生成エンジンを作り直し、「必要人数モデル」へ移行しました。店長が設定するのは曜日ごとの必要人数バンド（例: 6〜9時は1人、9〜17時は2人）だけで、勤務の開始時刻と長さもソルバーが解きます。決定変数は「クルー × 日付 × 勤務パターン」で、パターンを事前に列挙する方式を採りました。連続性や休憩がパターン側に内包されるので、モデルが素直になります。

性能面では目的関数の定式化で大きくつまずきました。最初は60秒使っても最適性を証明できず、項を1つずつ外して原因を切り分けた結果、希望充足の項が実は有害だったことが分かり削除。公平性も最大不足率の最小化から「労働時間の過不足（15分単位）」のL1型に変えたことで、労働時間の差が13.2時間から5.0時間まで縮まりました。デモ店舗のデータ（クルー8名・14日間・24時間営業）では、充足率97.7%・勤務80本を13.3秒でOPTIMALまで解けています。

## いま動いていること・今後

現時点で、希望提出から生成・編集・確定・PDF出力までの一連の流れはローカル環境で動いており、テストは現在115件書いています。一方で、まだ道半ばです。

- 実際の店舗での運用検証（デモデータでの確認までしか済んでいない）
- 店長向けアプリ（別リポジトリ予定・未着手）
- 交代時の勤務の重なりなど、既定値で仮置きしているパラメータの調整

「解いて間違えてはいけない部分はソルバー、あいまいさを扱う部分だけLLM」という線引きは、作りながら手応えを感じているところです。進捗があればまた記事にします。
