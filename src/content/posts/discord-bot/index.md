こんにちは、リラです。  
今回は、普段からずっと動かし続けている自作の多機能Discordボットを紹介します。

(リポジトリはトークン類を扱う運用リポジトリのため非公開です。この記事では仕組みと設計を紹介します)

## 概要

このボットは、友人とのDiscordサーバーで動かしている「なんでも屋」です。機能は大きく2つに分かれます。

- **スラッシュコマンド（24種類）** — 天気予報、Steamのセール・プロフィール検索、おみくじ、投票、サーバー内レベルシステム、Geminiに質問できる `/ask` など
- **バックグラウンド監視（ウォッチャー）** — 公式APIのないサイトを定期的にチェックし、変化があったら通知する機能。列車の空席監視、ウイスキーの販売情報検知、新刊ライトノベルの毎朝通知など

この記事では特に後者、**「APIのないサイトを『通知』に変える」** 部分に焦点を当てます。

## なぜ作ったか

きっかけは単純で、「e5489（JR西日本の予約サイト）で満席の観光列車をずっとリロードして空席を待つのがつらい」というものでした。予約サイトには空席通知の仕組みがなく、公開APIもありません。

同じような「人間が定期的に見に行くしかない情報」は他にもたくさんあります。ウイスキーの入荷情報、ライトノベルの発売日などです。それなら、**ブラウザで見に行く作業をボットに代行させて、変化があったときだけ通知してもらえばいい**と考えました。

## 技術構成

- **TypeScript + discord.js 14** — ボット本体。コマンドとイベントはファイル単位で分割し、起動時にディレクトリを走査して自動登録します
- **better-sqlite3** — 監視対象・通知済みIDなどの永続化（WALモード）
- **Puppeteer** — JavaScriptレンダリングが必要なページの取得
- **cheerio** — 静的なHTMLのパース
- **Docker** — 本番はコンテナで常駐運用

監視系はどれも「取得 → 判定 → 状態と比較 → 通知」という同じ流れなので、この共通パターンを軸に3つの実装を紹介します。

## 工夫した点

### 1. 対象サイトに負荷をかけないポーリング

スクレイピングはあくまで個人利用の範囲で、対象サイトに迷惑をかけないことを最優先にしています。空席監視ではチェック間隔を5分と長めに取り、さらに±1分のゆらぎ（ジッター）を入れて機械的なアクセスパターンを緩和しています。

```typescript
const CHECK_INTERVAL_MS = 5 * 60 * 1000;    // 基本間隔 5分
const JITTER_MS = 1 * 60 * 1000;            // ±1分のゆらぎ (機械的アクセスの緩和)

const scheduleNext = () => {
    const wait = CHECK_INTERVAL_MS + (Math.random() * 2 - 1) * JITTER_MS;
    setTimeout(async () => {
        await runAllChecks(client);
        scheduleNext();
    }, wait);
};
```

他にも、

- サイトの受付時間外（深夜帯）はチェック自体をスキップ
- 監視登録は1人5件まで
- 乗車日を過ぎた監視はDBから自動削除

といった制御を入れて、無駄なアクセスが積み上がらないようにしています。

### 2. SQLiteで「差分」と「重複通知」を管理する

通知系で一番大事なのは「同じ通知を何度も送らない」ことです。このボットではbetter-sqlite3で状態を持たせています。

ウイスキー監視では、通知済みのIDをテーブルに記録して重複を弾き、古いレコードは定期的に掃除します。

```typescript
export function markSeen(tweetId: string): void {
    getDatabase().prepare(
        'INSERT OR IGNORE INTO whisky_seen (tweet_id, seen_at) VALUES (?, ?)'
    ).run(tweetId, Date.now());
}

/** 30日より古い既読レコードを掃除 (DB肥大防止) */
export function pruneSeen(): void {
    const cutoff = Date.now() - 30 * 24 * 60 * 60 * 1000;
    getDatabase().prepare('DELETE FROM whisky_seen WHERE seen_at < ?').run(cutoff);
}
```

空席監視のほうは「空席あり」が続いている間に通知が連発しないよう、監視ごとに最終通知時刻を記録し、1時間のクールダウンを設けています。

### 3. 通知の届け先はDiscordとLINEの二段構え

Discordを開いていないときでも気付けるように、空席通知はDiscordのチャンネルに加えてLINE（Messaging APIのbroadcast）にも同報しています。LINE Notifyが2025年3月に終了したため、後継としてMessaging APIを採用しました。公式アカウントを友だち追加した人全員に届く形です。

### 4. 判定ロジックはページ構造に合わせて泥臭く

e5489の検索結果は空席状況がアイコン画像で表示されるため、Puppeteerでページを開いた後、`img` 要素をaltテキストに置き換えてから本文を取り出し、「空席あり」「満席」などの文言で判定しています。グリーン車だけ監視したい場合のために、設備名と空席状況をペアリングして特定の設備だけを見る仕組みも入れました。

ウイスキー監視は少し毛色が違い、X上の投稿を検索して、Geminiに「実際に購入できる販売情報か、ただの感想や転売か」をJSONで分類させています。キーワード検索だけではノイズだらけになるところを、LLMをフィルタとして挟むことで実用的な精度になりました。

## つまずいた点

- **リンクがスマホで壊れる** — e5489のURLは駅名がShift-JISエンコードされており、スマホのDiscordがURLを正規化すると壊れてしまいました。リンクボタンとコピー用URLの両方を載せることで回避しています
- **ページ構造への依存** — スクレイピングは相手のHTML構造が変わると壊れます。判定不能な場合は「UNKNOWN」としてログに残し、アイコンが取れないときは文字列判定にフォールバックするなど、静かに壊れないことを意識しました

## まとめ

「APIがないから自動化できない」と思っていた情報も、ゆるいポーリングと差分管理さえ丁寧に作れば、ちゃんと「通知」に変えられます。ポイントは次の3つでした。

- 対象サイトへの配慮（長めの間隔、ジッター、時間外スキップ、件数制限）
- SQLiteによる状態管理で重複通知を防ぐ
- 通知経路を複数持つ（Discord + LINE）

ボット自体は個人サーバーで動かしている運用リポジトリのため非公開ですが、仕組みについて質問があればお気軽にどうぞ。
